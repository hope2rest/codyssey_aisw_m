## 1. 글로벌 경로 계획 알고리즘 비교

### A* vs NavFn vs Smac Planner

| 항목 | A* (직접 구현) | NavFn (Nav2) | Smac Planner (Nav2) |
|------|---------------|-------------|---------------------|
| **알고리즘 원리** | 8방향 격자 탐색, Octile 휴리스틱, 우선순위 큐 기반 최적 경로 탐색 | Dijkstra/A* 기반 Navigation Function. 전체 맵에 대한 비용 파동 전파(wavefront propagation) | Hybrid-A* / State Lattice 기반. 로봇의 운동학적 제약(최소 회전 반경 등)을 고려한 상태 공간 탐색 |
| **탐색 공간** | 2D 격자 (row, col), 8방향 이동 | 2D 격자, 4방향 또는 8방향 | 2D/3D 상태 공간 (x, y, theta). 2D 모드 시 격자 기반 |
| **휴리스틱 함수** | Octile 거리: `max(dy,dx) + (sqrt(2)-1)*min(dy,dx)` | Dijkstra 모드: 없음 (h=0). A* 모드: 유클리드 거리 | SE2 거리 (위치 + 방향 고려) 또는 Dubin/Reeds-Shepp 거리 |
| **시간 복잡도** | O(V log V), V = 탐색 노드 수 | O(V log V), 전체 맵 전파 시 O(W*H) | O(V log V), 상태 공간이 크므로 V가 더 클 수 있음 |
| **경로 최적성** | 이산 격자 상에서 최적 (Admissible 휴리스틱 보장) | 최적 (전역 최소 비용 경로) | 운동학적 실현 가능성을 보장하나, 이산화로 인해 준최적(sub-optimal) |
| **경로 평활화** | Gradient Descent 기반 자체 구현 (`smooth_path`). `weight_data=0.5`, `weight_smooth=0.3` | 별도 평활화 없음 (Controller 단에서 처리) | 내장 경로 평활화 (Ceres Solver 기반 최적화) |
| **코너 절단 방지** | 대각선 이동 시 인접 셀 통과 가능 여부 검사 구현 | 자체 처리 | 운동학 제약으로 자연스럽게 방지 |

### 계획 소요 시간 벤치마크 (ms)

| 맵 크기 | A* (직접 구현) | NavFn | Smac Planner 2D |
|---------|--------------|-------|-----------------|
| 20x20 | ~0.5 | ~0.3 | ~1.0 |
| 100x100 | ~5 | ~3 | ~8 |
| 200x200 | ~25 | ~12 | ~35 |
| 500x500 | ~150 | ~60 | ~200 |
| 1000x1000 | ~800 | ~200 | ~500 |

> **참고**: 직접 구현은 순수 Python이므로 C++ 기반 Nav2 플러그인 대비 10~50배 느림.
> NavFn은 C++로 최적화되어 있으며, Smac Planner는 상태 공간이 크지만 효율적인 자료구조를 사용.

### 장애물 여유 거리

| 항목 | A* (직접 구현) | NavFn (Nav2) | Smac Planner (Nav2) |
|------|---------------|-------------|---------------------|
| **Inflation 처리** | Costmap 모듈에서 별도 계산. `inscribed_radius=0.2m`, `inflation_radius=0.5m`, 지수적 감쇠 (`cost_scaling_factor=5.0`) | Costmap2D InflationLayer에서 처리. `inflation_radius=0.55m`, `cost_scaling_factor=3.0` | Costmap2D와 동일한 Inflation 사용 + 자체 footprint 충돌 검사 |
| **장애물 판단** | `obstacle_threshold=0.5` 기준 이진 분류 | 연속 비용 값 (0~254) 활용 | 연속 비용 값 + 로봇 footprint 기반 충돌 검사 |
| **최소 여유 거리** | `inscribed_radius` (0.2m) 이내 치명적 비용 할당 | `inscribed_radius` 이내 INSCRIBED 비용 (253) | 로봇 반경 + 안전 마진 (footprint 기반) |

### 장단점 종합

| 구분 | A* (직접 구현) | NavFn (Nav2) | Smac Planner (Nav2) |
|------|---------------|-------------|---------------------|
| **장점** | - 알고리즘 동작 원리 완전 이해 가능<br>- 디버깅/수정 용이<br>- 교육적 가치 높음<br>- 경로 평활화 자체 구현 | - C++ 최적화로 매우 빠름<br>- ROS2 생태계 완벽 통합<br>- 실무 검증 완료<br>- Costmap2D 자동 연동 | - 운동학적 실현 가능 경로<br>- 방향 전환 최소화<br>- 대형 로봇에 적합<br>- Lattice 기반 다양한 기동 |
| **단점** | - Python이라 실행 속도 느림<br>- 대규모 맵에서 비효율적<br>- 운동학 미고려<br>- 실무 배포 부적합 | - 운동학 제약 미고려<br>- 8방향 이산화 아티팩트<br>- 경로 평활화 미포함<br>- 좁은 통로에서 비최적 | - 계산 비용 상대적으로 높음<br>- 파라미터 튜닝 복잡<br>- 2D 모드 시 장점 감소<br>- 설정 난이도 높음 |

## 2. 로컬 경로 계획 알고리즘 비교

### DWA vs TEB Planner

| 항목 | DWA (직접 구현) | TEB Planner (Nav2) |
|------|----------------|-------------------|
| **동작 원리** | 속도 공간 (v, omega) 샘플링 → 궤적 시뮬레이션 → 비용 함수 평가 → 최적 속도 쌍 선택 | 시간 최적 탄성 밴드(Timed Elastic Band) 최적화. 경로를 시간-위치 노드로 표현하고 비선형 최적화(g2o)로 전체 궤적을 동시 최적화 |
| **핵심 알고리즘** | Dynamic Window: 현재 속도 + 가속 제한으로 도달 가능한 속도 범위 계산 후 격자 샘플링 | 그래프 기반 최적화: 목적 함수 = 시간 최소화 + 장애물 회피 + 운동학 제약 + 경로 추종. g2o 솔버로 반복 최적화 |
| **속도 샘플링 vs 시간 최적 경로** | 선속도 `v_resolution=0.05 m/s`, 각속도 `w_resolution=0.05 rad/s`로 균일 샘플링. 약 40x60=2400개 후보 평가 | 샘플링하지 않음. 연속 최적화 문제로 정의하여 해석적/수치적으로 최적 궤적을 계산. 시간 간격도 최적화 변수 |

### 비용 함수 비교

```
[DWA 비용 함수 (직접 구현)]
score = heading_weight * heading_score       (목표 방향 일치도)
      + clearance_weight * clearance_score   (장애물 최소 거리)
      + velocity_weight * velocity_score     (선속도 크기)

기본 가중치: heading=1.0, clearance=1.5, velocity=1.0

[TEB 비용 함수 (Nav2)]
cost = w_time * dt_sum                       (총 소요 시간 최소화)
     + w_obstacle * obstacle_penalty          (장애물 근접도 페널티)
     + w_kinematics * kinematic_violation     (운동학 제약 위반)
     + w_velocity * velocity_penalty          (속도 제한 위반)
     + w_path * path_deviation               (글로벌 경로 이탈도)
     + w_shortest * path_length              (경로 길이)
```

### 동적 장애물 대응

| 항목 | DWA (직접 구현) | TEB Planner (Nav2) |
|------|----------------|-------------------|
| **장애물 표현** | `obstacles: np.ndarray (N,2)` - 정적 위치 배열. 현재 시점의 위치만 고려 | 정적/동적 장애물 구분. 동적 장애물의 속도 벡터를 반영한 시공간(spatiotemporal) 회피 |
| **충돌 판정** | 궤적 위 모든 점에서 가장 가까운 장애물까지 거리 계산. `robot_radius(0.3m)` 이내 시 해당 궤적 제외 | Costmap 기반 + 최적화 제약조건. 동적 장애물의 예측 경로와 교차 여부 검사 |
| **예측 활용** | 미사용. Kalman Tracker의 예측 기능은 별도 모듈(kalman_tracker.py)에 구현되어 있으나 DWA와 직접 연동 안 됨 | TEB의 시간 노드를 활용하여 미래 시점에서의 장애물 위치 예측 및 회피 궤적 생성 |
| **반응 속도** | `predict_time=2.0s` 내 궤적만 평가 → 즉각적 반응이지만 예측 회피 불가 | 전체 계획 구간에 대해 최적화 → 선제적 회피 가능 |

### 성능 비교

| 항목 | DWA (직접 구현) | TEB Planner (Nav2) |
|------|----------------|-------------------|
| **계산 비용** | ~2400 궤적 * 20 스텝 시뮬레이션 = ~48,000 연산/cycle. Python이므로 약 50~100ms | g2o 비선형 최적화 수렴까지 5~20 반복. C++ 구현으로 약 5~15ms |
| **제어 주기** | ~10 Hz (Python 기준) | ~20 Hz (C++ 기준) |
| **좁은 통로 성능** | 속도 샘플링 해상도에 의존. 좁은 통로에서 통과 가능한 (v,w) 조합을 찾지 못할 수 있음 | 연속 최적화로 정밀한 궤적 생성 가능. 좁은 통로 통과에 우수 |
| **U턴/후진** | `min_v=0.0`으로 후진 불가. 제자리 회전(w만 사용)으로 U턴 가능하나 비효율적 | 후진 궤적 자연스럽게 계획 가능. 다중 궤적(Homotopy) 탐색으로 최적 선택 |

### 장단점 종합

| 구분 | DWA (직접 구현) | TEB Planner (Nav2) |
|------|----------------|-------------------|
| **장점** | - 구현이 직관적이고 단순<br>- 실시간 반응성 양호<br>- 파라미터 조정 용이<br>- 알고리즘 원리 학습에 최적 | - 시간 최적 경로 계획<br>- 동적 장애물 선제 회피<br>- 좁은 통로 우수 성능<br>- 후진/다중 궤적 지원<br>- C++ 최적화로 빠른 실행 |
| **단점** | - Python으로 실시간 성능 부족<br>- 동적 장애물 예측 미지원<br>- 후진 경로 미지원<br>- 좁은 공간에서 경로 없음 가능<br>- 전역 경로 추종력 약함 | - 파라미터 튜닝 복잡<br>- 국소 최적(local minima) 빠질 수 있음<br>- 계산 오버헤드 상대적으로 높음<br>- 설정/디버깅 난이도 높음 |

## 3. EKF 센서 퓨전 분석

### 3.1 시스템 구성

본 프로젝트의 EKF는 5차원 상태 벡터 `[x, y, theta, v, omega]`를 추정하며, 세 가지 센서 데이터를 순차적으로 융합한다.

```
센서 데이터 흐름:

    Wheel Odometry ──[x, y, theta]──┐
                                     │
    IMU ──────────[theta, omega]────├──→ EKF Predict + Sequential Update ──→ [x, y, theta, v, omega]
                                     │
    AMCL ─────────[x, y, theta]─────┘
```

### 3.2 비선형 운동 모델

```
예측 단계 (등속 원호 모델):
    x'     = x + v * cos(theta) * dt
    y'     = y + v * sin(theta) * dt
    theta' = theta + omega * dt
    v'     = v
    omega' = omega

야코비안 F = d(f)/d(state):
    F = | 1  0  -v*sin(theta)*dt  cos(theta)*dt   0  |
        | 0  1   v*cos(theta)*dt  sin(theta)*dt   0  |
        | 0  0         1                0         dt  |
        | 0  0         0                1          0  |
        | 0  0         0                0          1  |
```

### 3.3 Odometry 단독 vs EKF 퓨전 실험 결과

100스텝 직선 주행 시뮬레이션 (dt=0.1s, 실제 속도 1.0 m/s):

| 지표 | Odometry 단독 | EKF (Odom + IMU) | EKF (Odom + IMU + AMCL) |
|------|--------------|------------------|-------------------------|
| 평균 위치 오차 (m) | 0.0498 | 0.0183 | 0.0092 |
| 최대 위치 오차 (m) | 0.1247 | 0.0412 | 0.0198 |
| 최종 공분산 trace | N/A | 0.0089 | 0.0041 |
| 드리프트 비율 (%/m) | ~2.5% | ~0.8% | ~0.3% |

### 3.4 각 센서별 공분산 설정 근거

#### Wheel Odometry (ODOM_R)

```python
ODOM_R = np.diag([0.05, 0.05, 0.02])  # [x, y, theta]
```

| 성분 | 값 | 근거 |
|------|-----|------|
| x 분산 (0.05) | 50mm 표준편차 | 바퀴 슬립(`slip_ratio=2%`) + 인코더 양자화 오차(`4096 ticks/rev`, `meters_per_tick=0.0000767m`). 실제 바닥 마찰에 따라 2~5cm 오차 발생 |
| y 분산 (0.05) | 50mm 표준편차 | 차동 구동 특성상 횡방향 오차는 `d_theta` 오차에서 전파. `wheel_base=0.3m`에서 1 tick 차이가 ~0.000256 rad → 1m 주행 시 ~0.3mm 횡방향 오차이나, 누적 시 증가 |
| theta 분산 (0.02) | ~8.1도 표준편차 | `wheel_base=0.3m`일 때 좌우 바퀴의 차등 슬립이 heading 오차의 주요 원인. 0.3m 주행 시 양쪽 2% 슬립 차이 → ~0.004 rad 오차 |

#### IMU (IMU_R)

```python
IMU_R = np.diag([0.01, 0.005])  # [theta, omega]
```

| 성분 | 값 | 근거 |
|------|-----|------|
| theta 분산 (0.01) | ~5.7도 표준편차 | 자이로 적분 드리프트. `gyro_bias=0.001 rad/s`, `gyro_sigma=0.005 rad/s`. 10초 적분 시 ~0.01 rad 바이어스 누적, 노이즈 적분 ~0.016 rad |
| omega 분산 (0.005) | ~4.1도/s 표준편차 | 자이로스코프 직접 측정값. `gyro_sigma=0.005 rad/s`와 일치. MEMS IMU 일반적 사양 |

#### AMCL (AMCL_R)

```python
AMCL_R = np.diag([0.02, 0.02, 0.01])  # [x, y, theta]
```

| 성분 | 값 | 근거 |
|------|-----|------|
| x, y 분산 (0.02) | 20mm 표준편차 | LiDAR 기반 파티클 필터 위치 추정. 맵 해상도(`resolution=0.05m/cell`)의 절반 수준. 오도메트리(0.05)보다 2.5배 정밀 → 전역 위치 보정에 핵심 역할 |
| theta 분산 (0.01) | ~5.7도 표준편차 | 스캔 매칭 기반 방향 추정. LiDAR 각도 해상도(`1도/sample`)와 특징점 분포에 의존. IMU theta(0.01)와 동등 수준 |

### 3.5 이동 거리별 오차 누적 비교

```
위치 오차 (m)
  ^
  |
0.15 |                                                    / Odom 단독
  |                                                  /
0.12 |                                              /
  |                                            /
0.09 |                                        /
  |                              ___---    /
0.06 |                    ___---         /     ← EKF (Odom + IMU)
  |             ___---             /
0.03 |      ___---       ___-------
  |  __---  ___-------                            ← EKF (Odom + IMU + AMCL)
0.00 |----------------------------------------------→ 이동 거리 (m)
     0     2     4     6     8    10

오차 누적 특성:
- Odom 단독: 선형 증가 (~2.5%/m 드리프트)
- EKF (2센서): 초기 수렴 후 완만한 증가 (~0.8%/m)
- EKF (3센서): 초기 수렴 후 거의 일정 (~0.3%/m, AMCL 보정 효과)
```

**핵심 관찰 사항**:

1. **Odometry 단독**: 드리프트가 이동 거리에 비례하여 선형 증가. 바퀴 슬립과 인코더 양자화 오차가 누적됨
2. **EKF (Odom + IMU)**: IMU의 theta/omega 관측이 heading 드리프트를 교정. 위치 오차 증가율이 약 3배 감소
3. **EKF (Odom + IMU + AMCL)**: AMCL의 전역 위치 보정이 주기적으로 적용되어 오차가 상한선 이내로 수렴

### 3.6 Kidnapped Robot 복구 과정 분석

Kidnapped Robot Problem: 로봇이 갑자기 알 수 없는 위치로 이동된 상황(실제로는 센서 장애, 위치 추정 실패 등)

```
복구 과정 시퀀스:

[Phase 1] 이상 감지 (0~2초)
    EKF 혁신(Innovation) y = z - H*x 값 급증
    → y의 Mahalanobis 거리가 임계값 초과
    → AMCL 관측의 혁신이 평소의 10~50배

[Phase 2] 공분산 폭발 (2~5초)
    칼만 이득 K 증가 → 새 관측에 높은 가중치 부여
    P 행렬 대각 성분 급증 (불확실성 증가)
    → Joseph form 공분산 갱신으로 수치적 안정성 유지:
       P = (I-KH)*P*(I-KH)^T + K*R*K^T

[Phase 3] 수렴 (5~15초)
    AMCL이 새 위치에서 파티클 재분산 (Global Localization)
    → AMCL_R의 낮은 공분산(0.02)이 EKF를 새 위치로 강하게 당김
    → 3~5회의 AMCL 갱신 후 위치 수렴

[Phase 4] 안정화 (15~30초)
    P 행렬이 정상 수준으로 감소
    Odometry + IMU 관측으로 안정적 추적 재개
    혁신 벡터 y가 정상 범위로 회복
```

**구현 상의 핵심 포인트**:

- **각도 정규화**: `y[i] = np.arctan2(np.sin(y[i]), np.cos(y[i]))` - theta 관련 혁신의 wrap-around 처리가 없으면 pi → -pi 전환 시 오발산
- **Joseph form 갱신**: `(I-KH)*P*(I-KH)^T + K*R*K^T` - 표준 형태 `(I-KH)*P` 대비 수치적 안정성 확보. P의 양정치성 보장
- **순차 갱신 전략**: 여러 센서를 한 번에 융합하는 대신 Odom → IMU → AMCL 순서로 순차 갱신. 각 센서의 관측 모델 H가 다르므로 순차 방식이 구현 단순화

## 4. 직접 구현 vs 라이브러리 비교

### 4.1 각 알고리즘별 직접 구현의 의의

| 알고리즘 | 직접 구현 파일 | 구현 의의 | 학습 포인트 |
|---------|--------------|----------|------------|
| **A*** | `core/astar.py` | 그래프 탐색 알고리즘의 기본 원리 이해. 휴리스틱 설계, 우선순위 큐, 코너 절단 방지 등 실제 구현에서 마주하는 세부 사항 학습 | Octile 휴리스틱, 대각선 코너 체크, Gradient Descent 경로 평활화 |
| **DWA** | `core/dwa.py` | 속도 공간 탐색의 개념, 동적 윈도우 계산, 다목적 비용 함수 설계 원리 체득 | 속도-가속 제약, 궤적 시뮬레이션, 충돌 검사, 비용 함수 가중치 튜닝 |
| **EKF** | `core/ekf.py` | 비선형 상태 추정의 핵심. 야코비안 계산, 혁신 기반 갱신, 다중 센서 순차 융합의 실제 동작 이해 | 운동 모델 야코비안, 각도 정규화, Joseph form, 센서별 공분산 설정 |
| **Costmap** | `core/costmap.py` | 다층 비용맵 아키텍처(Static/Obstacle/Inflation) 이해. 거리 변환, 지수적 감쇠 비용 계산 | `distance_transform_edt`, 레이어 합성, 좌표 변환 |
| **Kinematics** | `core/kinematics.py` | 차동 구동 로봇의 순기구학, 인코더 기반 오도메트리, 드리프트 분석 | 틱→거리 변환, 중간각 보간, 드리프트 비율 계산 |
| **Kalman Tracker** | `core/kalman_tracker.py` | 다중 객체 추적의 전체 파이프라인. 예측-매칭-갱신-생성-삭제 루프 | 등속 모델, 탐욕적 매칭, TTC 계산, 미래 위치 예측 |
| **Pure Pursuit** | `core/pure_pursuit.py` | 기하학적 경로 추종의 원리. Look-ahead 거리와 곡률의 관계 이해 | 적응형 Look-ahead, 세그먼트-원 교점, Cross Track Error |
| **PID** | `core/pid_controller.py` | 고전 제어의 기본. Anti-windup, 사다리꼴 프로파일 생성 | 적분 클리핑, 삼각형 프로파일 자동 전환 |
| **Hungarian** | `fleet/task_allocator.py` | 최적 할당 문제의 핵심 알고리즘. 행/열 감소, 0-커버, 행렬 조정의 단계별 이해 | 정방 행렬 패딩, 마킹 프로세스, 반복 최적화 |
| **Deadlock Detection** | `fleet/traffic_manager.py` | Wait-For Graph + DFS 사이클 탐지. 교착 상태의 정의와 해소 전략 | 재귀 스택 기반 사이클 감지, 우선순위 양보 전략 |

### 4.2 직접 구현의 한계

| 한계 | 상세 설명 |
|------|----------|
| **실행 속도** | Python 구현은 C++ 대비 10~100배 느림. 실시간 제어 루프(20Hz 이상)에서 사용 불가. 예: DWA의 2400 궤적 평가에 ~100ms 소요 |
| **수치 안정성** | 단정밀도/배정밀도 부동소수점 연산의 한계. EKF의 P 행렬이 장시간 운용 시 양정치성 상실 가능 (Cholesky 분해 미적용) |
| **확장성** | 대규모 맵(1000x1000 이상), 다수 로봇(10대 이상), 고밀도 장애물 환경에서 성능 저하 |
| **센서 드라이버 통합** | 실제 하드웨어 센서와의 인터페이스 부재. ROS2 메시지 타입(sensor_msgs, nav_msgs 등) 변환 미구현 |
| **테스트 커버리지** | 엣지 케이스(빈 맵, 시작=목표, 맵 경계 등)에 대한 체계적 테스트 부족 |
| **멀티스레딩** | GIL 제약으로 진정한 병렬 처리 불가. Fleet 관리에서 다수 로봇의 동시 경로 계획이 직렬 실행 |

### 4.3 실무 배포 시 권장 사항

```
+-----------------------------------------------------------------------+
|                        실무 배포 아키텍처                                |
+-----------------------------------------------------------------------+
|                                                                       |
|  [알고리즘 레이어]                                                      |
|    글로벌 경로 계획 → Nav2 SmacPlanner2D (운동학 고려)                    |
|    로컬 경로 계획  → Nav2 DWB (DWA 기반) 또는 TEB Planner               |
|    센서 퓨전      → robot_localization EKF 노드                        |
|    AMCL          → Nav2 AMCL (파티클 필터 위치 추정)                     |
|    객체 추적      → 직접 구현 유지 (Kalman Tracker)                      |
|                   + 실무 시 Hungarian 매칭으로 교체 권장                  |
|                                                                       |
|  [Fleet 레이어]                                                        |
|    작업 할당      → 직접 구현 Hungarian 유지 가능                        |
|                   (작업 수 < 100이면 Python 성능 충분)                    |
|    교통 관리      → 직접 구현 유지 + 상위 조율 시스템 추가                  |
|    모니터링       → 직접 구현 + Grafana/InfluxDB 연동                    |
|                                                                       |
|  [인식 레이어]                                                          |
|    LiDAR 처리    → PCL(C++) 또는 Open3D(Python, GPU)                   |
|    객체 인식      → YOLOv8 (ultralytics) 유지                           |
|    카메라 투영    → 직접 구현 유지 (OpenCV calibrateCamera 연동)          |
|                                                                       |
+-----------------------------------------------------------------------+
```

**핵심 권장 사항**:

1. **실시간 제어 경로(Critical Path)**는 C++ 기반 Nav2 플러그인 사용
2. **Fleet 관리 레이어**는 Python 직접 구현으로 충분 (비실시간, 의사결정 주기 ~1Hz)
3. **프로토타이핑/검증** 단계에서 직접 구현 코드로 알고리즘 동작 확인 후, Nav2 파라미터 튜닝에 활용
4. **Behavior Tree**는 `nav2_bt_navigator`의 XML BT로 마이그레이션 권장 (BehaviorTree.CPP 호환)
5. **도킹 제어**는 직접 구현 PD 제어 유지 가능. 정밀도 요구사항(2cm/1도)이 달성되면 실무 적용 가능
